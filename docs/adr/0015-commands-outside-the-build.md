# Side-effecting work lives in Commands, outside the build graph

Firmware workflows need `flash`, `run`, `debug` and `deploy`, which Kbuild-style projects express as `.PHONY` targets. ADR-0014 forbids `.PHONY` because an Action without outputs cannot be cached or verified. Instead, Commands are declared (`run-flash := ...`) in a single committed `.makit/commands.mk`, never in Build files, and run with `makit run flash`. Command names are therefore project-wide; variants get distinct names (`flash-jlink`, `flash-stlink`) rather than per-machine overrides, since `.makit/` holds no local files. A Command may depend on Goals, which are built first, but it is never cached or sandboxed and never produces Goals. Declared Tools can also be invoked directly with `makit tool <NAME> run [args...]`, so users run exactly the binary the build uses. Keeping side effects out of the graph is what lets every Action stay deterministic and cacheable.

The prefix is `run-*`, not `cmd-*`: Kbuild's `cmd_*` means a *build* command template (a Rule in Makit's terms), and a dash-vs-underscore distinction is too fragile to carry opposite meanings. `cmd_*` / `quiet_cmd_*` in a Build file are rejected with a hint pointing to Make rule syntax. `makit tool <NAME> run` runs with the user's environment, unsandboxed. Toolchain tools (`CC`, `CARGO`, …) require `-O <output tree>` to know which Toolchain is selected; `[tools]` entries do not.
